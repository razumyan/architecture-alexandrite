## Проблемные места в архитектуре

1. Отсутвует система мониторинга. Отсутствие информации о том, что происходит в системе, делает поиск проблем медленным.
2. Управление состоянием заказа "размазано" по разным приложениям, что может вызвать несогласованность данных.
   При конкурентных изменениях состояния заказа в CMS API и MES API может произойти неоднозначность сохраненного
   статуса.
3. Появление заказа может отслеживаться только со стороны CRM API (вручную или по расписанию), что может вызвать потери
   при обработке новых заказов. Например, не ясно как статус SUBMITTED переходит в PRICE_CALCULATED.
4. Rabbit MQ лежит только в связке CRM API и MES API, что не дает возможности однозначно трактовать состояние заказа в
   Shop DB и MES DB.

## Инициативы для устранения проблем

1. Настроить очереди на Rabbit MQ, чтобы добиться однозначности по управлению статусами заказов (Atomic Broadcast)
2. Реализовать взаимодействие Shop API и CRM API в контексте управления статусами заказов.
    1. Провести анализ кодовой базы, для выработки лучшей стратегии взаимодействия (REST, CQRS)
    2. Реализовать взаимодействие используя текущие технологии (Spring Boot)
3. Реализовать систему трекинга, для отслеживания изменения статуса заказа между системами.
4. Реализовать систему мониторинга, для отслеживания отказов в работе системы и их причин.
5. Внедрить принципы Backpressure и CircuitBreaker во все API.
6. По возможности выделить из сервиса MES компонент оценки заказа, чтобы разделить обслуживание API-пользователей и
   алгоритм расчета заказа. Это повысит масштабируемость системы.
